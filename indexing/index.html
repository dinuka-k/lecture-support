    How database indexing works

    The ideas

    • A table is stored on disk as a file split into pages (blocks). The disk always reads whole pages.
    • The CPU can only check rows that are in RAM, so pages are first copied into the buffer pool. RAM is fast but small; when it is full the least recently used page is evicted.
    • A disk read is roughly 100,000× slower than a RAM access, so a query's speed is mostly the number of pages it reads from disk.
    • Full table scan: rows are not sorted, so every page must be read and every row checked.
    • Index: a separate, sorted structure of key → (page, slot). The root narrows the search to one leaf, binary search finds the entry, and only one data page is read.
    • An index only helps queries on its column: a WHERE name = … query can't use an index on id.

    Simplifications

    • In the animation every page read costs the same. Real disks stream neighbouring pages faster, which is why a full scan can win on tiny tables (see Bigger tables).
    • The table has no constraints, so without an index the database can't know an id is unique and keeps scanning after a match. Switch on LIMIT 1 (next to the query) to stop at the first match.
