    Which join when?

    Nested loop
    Works for any join condition (<, >, ≠, LIKE …). Fine when one table is tiny — or when the inner table has an index on the join column (index nested loop).
    Hash join
    The usual choice for equality joins (=) on big, unsorted tables. Needs RAM for a hash table on the smaller table.
    Merge join
    Best when both inputs already come sorted on the key (an index, or an earlier ORDER BY): then it is a single pass. Its output is sorted too.

    How a database joins two tables

    The ideas

    • A join pairs the rows of two tables that satisfy a condition — here s.dept = d.id. An inner join outputs only the pairs that match, so a student whose department doesn't exist is left out.
    • The database can compute the same result in different ways. The query planner picks the cheapest one from the table sizes, the indexes and the memory available.
    • Nested loop: for each row of the outer table, scan the whole inner table. Always n × m comparisons — but it works for any condition.
    • Hash join: build a hash table on the smaller table, then probe it: each row of the other table looks in just one bucket. Roughly n + m work, but only for =, and the hash table needs memory.
    • Merge join: sort both tables on the key, then move two pointers forward together. The merge itself is at most n + m comparisons; the sorting costs about n log n — nothing if the input is already sorted.

    Simplifications

    • Everything is in RAM and the scoreboard counts operations. Real databases mostly count disk page reads — e.g. a block nested loop reads the inner table once per block of outer rows.
    • departments.id is unique, so the merge join never moves backwards. With duplicates on both sides it outputs every pair of the two matching groups.
    • Real hash tables have thousands of buckets. When the hash table doesn't fit in RAM, a Grace hash join first splits both tables into partitions on disk.
